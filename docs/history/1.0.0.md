## Milestones and tasks

### M14 — Maps and tokens

Scenes with a grid, tokens and fog of war, in the workspace centre.

- [x] **T-1401 · Scenes**
  - **Deps:** T-1301
  - **Do:** A `scenes` table (FR-MAP-01): name, background asset, size, grid type (square, hex) and size, and which scene is active for players. GMs and assistants create, edit, order and delete scenes; `scene.updated` events keep clients current. Players only see the active scene.
  - **Done when:** endpoint tests cover the scene life cycle, permissions and events.

- [x] **T-1402 · Map canvas**
  - **Deps:** T-1201, T-1401, Q18
  - **Do:** The scene renders in the workspace centre on a canvas (FR-MAP-02), with the renderer chosen in Q18 (an ADR): background, grid, pan and zoom by mouse, keyboard and touch. Rendering stays smooth on a mid-range phone.
  - **Done when:** web tests cover the scene model behind the canvas; e2e pans and zooms on desktop and phone viewports; a performance check with a large background and 100 tokens is recorded.
  - **Performance check (2026-10-30):** Chromium, software WebGL (SwiftShader; no GPU reaches the browser in development or CI), 4096 px background, 100 sprites standing in for tokens, panning and zooming every frame. Frame time p50/p95: 200 × 200 hex grid (120,799 edges) 68/95 ms on a desktop, 84/112 ms on a 390 × 844 phone viewport at 4× CPU throttling; 40 × 30 hex grid 47/64 and 60/68 ms; no grid 39/46 and 56/68 ms. Software rendering dominates these times, so they are an upper bound; a real mid-range phone is still to be checked (ADR-067).

- [x] **T-1403 · Tokens**
  - **Deps:** T-1402
  - **Do:** Tokens link to an actor (taking its image and name) or stand alone (FR-MAP-03). GMs place, hide and remove tokens; owners of the actor move its tokens; moves snap to the grid and show live to everyone who may see them. Hidden tokens are filtered on the server and never sent to players (NFR-08). Opening a token opens its actor's sheet in the workspace.
  - **Done when:** endpoint and wire tests cover placement, movement permissions and hidden tokens; e2e has a GM and a player moving tokens in two browsers.

- [x] **T-1404 · Fog of war**
  - **Deps:** T-1403
  - **Do:** GMs reveal and hide areas of a scene with shapes or grid cells (FR-MAP-04). Players receive only revealed areas, and tokens inside hidden areas are not sent to them. GMs see the fog as a tint.
  - **Done when:** wire tests prove hidden areas and the tokens in them never reach players; e2e reveals an area and a player sees it appear.
  - **Done (ADR-070):** scenes keep revealed rectangles; players get no token in the fog but their own actors'. The background image itself is not cut, so its address shows all of it.

- [x] **T-1405 · Token menu**
  - **Deps:** T-1403
  - **Do:** A right click on a token opens a menu with the token list's actions the member may take (open, hide or reveal, remove); Shift+F10 or the context-menu key opens it for the selected token (FR-MAP-03). Added at the user's request.
  - **Done when:** unit tests cover the menu's keys and closing; e2e reveals a hidden token from its menu and opens the menu by keyboard.

- [x] **T-1406 · Map toolbar and ruler**
  - **Deps:** T-1402
  - **Do:** A toolbar over the map switches between selecting, a ruler, a circle and a cone (FR-MAP-05). The ruler measures a path of points, and the circle and cone a radius or length from a point, between cells or anywhere on a gridless scene, in the scene's unit; scenes gain the distance a cell stands for, its unit and how diagonals count (ADR-069). Only the member measuring sees the ruler. Added at the user's request.
  - **Done when:** unit tests cover the counting on square, hex and gridless scenes, each diagonal rule, paths and the cone's outline; e2e measures a path, a circle and a cone on a scene and the map does not pan while measuring.

### M15 — Plugin platform

Plugin data that follows system upgrades, and plugin code that runs contained.

- [x] **T-1501 · Plugin data migrations**
  - **Deps:** none
  - **Do:** A plugin ships `migrations/` (FR-PLUGIN-12): declarative steps per version (rename, move, set default, drop a field) and, for what they cannot express, a `migrate` hook in `code/server`. When a GM upgrades a table (ADR-058), the steps between each entity's `dataVersion` and the new version run on its documents, in a transaction per entity, and `dataVersion` is updated, so the sheet notice clears. A failed migration leaves the entity as it was and reports it.
  - **Done when:** validator tests cover the migration files; tests upgrade reference plugin fixtures across two versions, including a failing step; the authoring guide has a migrations section.

- [x] **T-1502 · Client code sandbox**
  - **Deps:** Q17
  - **Do:** `code/client` runs in a sandboxed iframe per custom node and card (Q17, ADR-074), and reaches sheets only through the `@vtt/sdk/client` hooks over a message bridge (FR-PLUGIN-13). Custom nodes and cards keep working for the reference plugins.
  - **Done when:** tests show client code cannot read the app's DOM, cookies or fetch the API; the reference plugins' custom nodes and cards work as before.

- [x] **T-1503 · Server code isolation**
  - **Deps:** none
  - **Do:** Plugin server code runs in an isolated runtime with no Node API reachable (no `require`, `process`, filesystem or network), keeping the worker per plugin and the time limits of ADR-047 (FR-PLUGIN-13).
  - **Done when:** tests show those APIs are unreachable from shared and server code; the reference plugins' handlers, commands and hooks pass unchanged.

### M16 — Modules, a 5e study and the interface

Module plugins, a generic way to extend any table, a full system built as a test of the plugin format, the changes the two studies found (T-1607 to T-1614, T-1617 and T-1618), and a review of the interface before the 1.0 freeze with the changes it found (T-1619 and T-1620).

- [x] **T-1601 · Module plugins**
  - **Deps:** none
  - **Do:** Plugins of `kind: module` (FR-PLUGIN-16) extend any table, whatever its system, and change no system data. A module may ship a theme, stylesheets for named parts, client code for frames, settings and lang files; it may not ship types, sheets, rolls or packs. The validator checks modules like systems. Admins install and enable modules as they do systems, acknowledging code. GMs choose which enabled modules a table uses in its settings, and its members load them with the table. `settings.json` gains a `scope` per setting, for systems and modules alike: `instance` (set by admins on the Plugins page), `table` (set by the GM in table settings; the default, so today's system settings keep working) or `user` (set by each member for themselves on the table page). The app draws each form from the declarations and the server checks the values against them. Formulas keep reading table settings as `@settings`. Record the design in an ADR.
  - **Done when:** validator tests cover module files and refuse system-only files in a module; server tests cover enabling a module and choosing it for a table; a test module loads for that table's members only; tests cover each settings scope: who may set it, where it is stored, and that values outside the declaration are refused.

- [x] **T-1602 · Themes and named parts**
  - **Deps:** T-1601
  - **Do:** A module's `theme.json` sets the app's design tokens on the table page (colours, fonts, radius; light and dark), with images from its own files. Its stylesheets style the table page's named parts (`data-vtt-part`: chat, dock tabs, panels, map toolbar, sheet frame…), scoped to those parts; the app documents the names and keeps them stable across versions. Ship `plugins/parchment-skin` as an example.
  - **Done when:** web tests cover tokens and parts applied and removed with the module; e2e shows the example skin on a table and not on another; the authoring guide documents tokens and parts.

- [x] **T-1603 · Module frames: overlays, panels, events and actions**
  - **Deps:** T-1601
  - **Do:** Module client code runs in sandboxed frames, as ADR-074's do (no network, no access to the page), mounted at two places: overlays over the table page (click-through or interactive) and panels in the table workspace (in the Panels menu, dockable like Chat). Frames receive table events (rolls with the dice and results the server decided, chat messages, combat, scene and token changes), each only if the viewer may see it, so a frame shows results and never decides them; the chat never waits on a frame. Frames get the module's settings for the viewer, merged from instance, table and user scopes, and are told when they change; a frame may change only the viewer's own `user` settings. Through the SDK, a frame can act as the viewer: post a chat message, roll, open a sheet or journal entry, and the combat actions the viewer may take. The server checks each action as the viewer's own, and the app rate-limits them per frame. Each user can turn a table's overlays off.
  - **Done when:** tests show a frame gets no event the viewer may not see, cannot reach the page or the network, and cannot act beyond the viewer's rights; e2e covers an overlay and a panel from a test module, including a roll posted from the panel.

- [x] **T-1604 · 3D dice study**
  - **Deps:** T-1603
  - **Do:** Build `plugins/dice-3d`, our own module (three.js and a physics library bundled in, not dddice): an overlay that throws polyhedral d4–d20 and d100 for each roll the viewer sees and lands them on the server's results. Use only what the plugin format and the module SDK offer, and record each gap, workaround and rough edge in `docs/studies/dice-3d.md`. From the findings, propose follow-up tasks; those the user approves join M16.
  - **Done when:** the plugin validates, packs and installs; e2e rolls on a table with the module, sees the dice frame animate and the chat show the result at once, and the per-user switch hides the dice; the study lists its findings and the proposed tasks.

- [x] **T-1605 · D&D 5e SRD study**
  - **Deps:** none
  - **Do:** Build `plugins/dnd5e-srd` from the System Reference Document 5.2 (CC-BY-4.0, with its attribution): characters and NPCs with abilities, skills, saves, proficiency, attacks, spells and slots, conditions, rests and an SRD pack. Use only what the plugin format offers, and record each gap, workaround and rough edge in `docs/studies/srd5.md`. From the findings, propose follow-up tasks; those the user approves join M16.
  - **Done when:** the plugin validates, packs and installs; e2e makes a character, rolls an attack and casts a spell; the study lists its findings and the proposed tasks.

- [x] **T-1607 · Formulas: readable, with dice and text from data**
  - **Deps:** none
  - **Do:** From the [5e study](../studies/srd5.md#proposed-tasks), P1, P2 and P9. `@roll.resolved` prints only the branch a conditional or `if` took, with its values. A die's size may be a formula (`(@item.dice)d(@item.die)`), and a text field may hold a dice expression that a formula rolls (`roll(@item.damage)`), checked when it is saved. Built-in `text(x)` and `signed(x)`, and `+` joins text with numbers. `srd5` drops its chains of die sizes and its `damage()` shared function; `saveText()` names abilities, so it waits for T-1611.
  - **Done when:** tests cover each; a longsword's damage reads `1d10 + 3` in the chat; e2e rolls damage from a stored dice expression.

- [x] **T-1608 · Recipes: dice in outcomes, named values, actor types, several rolls**
  - **Deps:** T-1607
  - **Do:** From the [5e study](../studies/srd5.md#proposed-tasks), P4, P5, P7 and P10. Outcomes and cards read the kept dice (`@roll.dice`, `@roll.natural`), and a recipe can name values (`let`) that its formula, outcomes and card share. A recipe may list the actor types it is for; the validator checks it against those only, and the server refuses it for others. A recipe rolls named formulas in order into one card (an attack, then its damage, doubled on a critical). Formulas in an `items` row read the row's item as `@item.<field>`, so `visibleIf` and `args` can depend on it. `srd5` uses them: one attack button rolls attack and damage, and creatures lose the fields that existed only to validate.
  - **Done when:** tests cover each key; e2e attacks with one button and sees attack, damage and a critical in one card.

- [x] **T-1609 · Roll options**
  - **Deps:** T-1608
  - **Do:** From the [5e study](../studies/srd5.md#proposed-tasks), P3. A recipe declares options the app asks for when its button is pressed: a choice (Advantage, Normal, Disadvantage), a number (a slot level) or a bonus (`1d4`), read as `@options.<name>`, with defaults and shortcuts (Shift for Advantage, Ctrl for Disadvantage). The server checks the values against the declaration. `srd5` drops its "Next d20 rolls" field and casts spells at a higher slot.
  - **Done when:** tests cover the declaration and the checks; e2e rolls with Advantage by shortcut and upcasts a spell from the options.

- [x] **T-1616 · Rolling without the options dialog**
  - **Deps:** T-1609
  - **Do:** A personal preference, "Ask for roll options", on by default and kept with each table membership, so a player can choose differently at each table. Turned off, pressing a roll button whose recipe has options rolls at once with every option at its default, and Alt-click opens the dialog. Shift and Ctrl keep picking their choices either way.
  - **Done when:** tests cover both settings and the Alt key; e2e turns the preference off and rolls a 5e check without the dialog.

- [x] **T-1610 · Server code with items, derived values and bounds**
  - **Deps:** T-1608
  - **Do:** From the [5e study](../studies/srd5.md#proposed-tasks), P6 and P11. Handler recipes take `item` like formula recipes; handlers get the item, the actor's derived values and item totals; `ctx.items.adjust` steps an item's counters and `ctx.actors.set` sets a field that is not a counter, with the same rights as the roller. A counter's `minimum` and `maximum` may be formulas (`@hp.max`), checked on every step. `srd5` spends a slot when a spell is cast, recharges features on a rest, and stops healing at the maximum.
  - **Done when:** tests cover the new `ctx` calls, their rights and the bounds; e2e casts a spell and sees its slot spent.

- [x] **T-1611 · Labels for values, and translation**
  - **Deps:** T-1614
  - **Do:** From the [5e study](../studies/srd5.md#proposed-tasks), P8, and the [dice-3d study](../studies/dice-3d.md#proposed-tasks), P5. `enumLabels` gives a lang key per value for type fields and settings, so stored values stay plain; card rows translate values that are lang keys, so `srd5` drops its `saveText()` shared function; server code posts text by lang key with parameters, so each viewer reads it in their language. Settings gain a `colour` format drawn as a colour picker, and plugin code gets typed settings. Then translate `srd5` and `dice-3d` to pt-BR (the 5e study's Q3).
  - **Done when:** tests cover labels, translated card rows and server messages; e2e shows a pt-BR sheet, card and rest message.

- [x] **T-1612 · Module code: packaging, declared exports, system dice**
  - **Deps:** none
  - **Do:** From the [dice-3d study](../studies/dice-3d.md#proposed-tasks), P1, P3 and P6. The guide documents where `vtt-plugin pack` resolves npm imports and which files under `code/` it leaves out, with an example `code/package.json`; `pack` prints each bundle's size and warns above a threshold. A module declares its overlays and panels in its files, so the app needs no probe frame. Module frames get the table system's custom dice (faces, labels, values), and the guide documents die names (`d<sides>`, `d<NAME>`).
  - **Done when:** tests cover the declaration, the size warning and the dice given to frames; dice-3d loads with no probe frame and throws a system's custom die in e2e.

- [x] **T-1613 · Testing kits for plugin code**
  - **Deps:** T-1610, T-1612
  - **Do:** From the [dice-3d study](../studies/dice-3d.md#proposed-tasks), P7, and the [5e study](../studies/srd5.md#proposed-tasks), P13. `@vtt/sdk/client/testing` renders an overlay or panel with fake events, settings and actions and records what it asked for; `@vtt/sdk/testing` gives a fake handler `ctx` and a formula harness. The server's test support loads a reference plugin's compiled code. `dice-3d` and `srd5` use the kits in place of their own fakes.
  - **Done when:** both reference plugins test their components and handlers with the kits; the guide documents them.

- [x] **T-1614 · Attribution and packs; `srd5`**
  - **Deps:** none
  - **Do:** From the [5e study](../studies/srd5.md#proposed-tasks), P12, and its Q2. A manifest `attribution` (text and a link) shows on the Plugins page and in the Compendium beside each entry from the plugin's packs. Packs accept collections in the stored form (maps by id) as well as lists. Rename `dnd5e-srd` to `srd5` (folder, id, tests and docs), and give it its SRD attribution.
  - **Done when:** tests cover the attribution and both pack forms; e2e sees the attribution in the Compendium; nothing named `dnd5e-srd` is left.

- [x] **T-1617 · Card actions**
  - **Deps:** T-1608
  - **Do:** A card offers actions, such as "Apply damage" or "Take healing", that step a counter by an amount worked out when the roll is made. Whoever clicks applies it to the token they have selected on the map, if they may edit its actor: the GM selects the goblin and applies the damage, a player selects their own token and takes the healing. `srd5` applies attack damage or half of it, and spell damage or healing.
  - **Done when:** tests cover the actions and their rights; e2e applies an attack's damage to a selected token.
  - **Also:** a spell that asks for a saving throw offers to roll it for the selected token, against the spell's DC (at the user's request). Attacks roll their damage from the card, for the attacker and doubled on a critical hit, and the damage card applies it (at the user's request).

- [x] **T-1618 · Token statuses**
  - **Deps:** none
  - **Do:** From the [5e study](../studies/srd5.md#proposed-tasks), P15. An actor type declares boolean fields as statuses with an icon from the plugin's files; tokens, the token list and the combat tracker show those that are on, a secret field's only to GMs and assistants, and follow the sheet as it changes. `srd5` shows its conditions on tokens.
  - **Done when:** tests cover the declaration, who sees each status and their updates; e2e sets a condition on a sheet and sees it on the token.

  - **Deps:** T-1606

A disabled user cannot sign in and their sessions end. The last enabled admin cannot be disabled.

- [x] **T-1620 · Interface fixes**
  - **Deps:** T-1606
  - **Do:** From the [interface review](../studies/interface-review.md), P2 to P5, P7 and P8:
    - **Sheet grids** (R9): in `sheet-renderer`, a counter keeps a minimum width for its value, a grid wraps to fewer columns when its cells are narrower than its fields need, and long labels wrap without overlapping the field below, for every system.
    - **Roll lines** (R10): a roll in chat shows its resolved formula (`1d20 + 4`), then the dice and the total. The recipe's formula, with its references, shows only on request, such as in a "Formula" disclosure.
    - **Map legibility** (R11, R12): token names draw on a solid pill readable in both themes; status icons get a ring that shows them in the dark theme; names and statuses stay shown at every zoom and keep their size on the map, at the user's request; the grid's colour comes from the theme.
    - **Narrow panels** (R13, R16, R19): journal, combat and member rows put their controls below the name rather than truncating it; the tracker shows initiative once, as a field the GM edits; rows and type filters show the system's translated type label; an item's **Give** list starts on "Choose an actor".
    - **Keyboard** (R22, R23): panel tabs show the focus ring; F6 and Shift+F6 move between panel groups; a "Skip to panel" menu lists the open panels; the dock sits in a `main` landmark. The keys are documented in the user guide.
    - **Small fixes** (R2, R3, R6, R7, R8, R15, R21): a "Page not found" page; the invite page names the table and its GM, with **Sign in** as a button; plural issue counts, and **Enable** after the badges on narrow screens; one filled button per form, and no save button for an empty section; **End encounter** asks first and sits apart from the turn buttons, and adding a combatant opens from an **Add** button; one button style for card and panel actions; the system's version only on the Settings and Plugins pages.
    - **Dropped:** R20 (copying invite links from the list, with when they were made and how often used), at the user's request: invites keep only a hash of their token, so a link shows once, when it is made.
  - **Done when:** component and web tests cover each part (a counter in a narrow grid, no `@` reference in a default roll line, map colours from the theme, type labels, initiative shown once, **Give** without a choice, F6 both ways and the skip menu, and each small fix); e2e reaches the chat input from the header in a few keys; the capture script's screenshots show the changes at both sizes and in both themes.

### M17 — 1.0

The plugin API promise, a security review, then the release. The project has no users to upgrade yet, so 1.0 promises no upgrade path from 0.x data.

- [x] **T-1701 · Plugin API freeze**
  - **Deps:** M12–M16, Q19
  - **Do:** Set `CORE_API_VERSION` to `1.0.0` and document what 1.x keeps compatible (manifest, file formats, SDK, `ctx`, module themes, named parts, settings scopes, frame events and actions). Plugins for 0.x load as Q19 decides. The reference plugins and the guide move to `^1.0.0`.
  - **Done when:** the compatibility promise is in the guide and an ADR; tests cover loading plugins declaring each supported range.

- [x] **T-1703 · Security review and hardening**
  - **Deps:** M12–M16
  - **Do:** Review the surfaces added since 0.2.0: uploads, scenes and tokens on the wire, fog filtering, the client sandbox, server isolation, and module themes, frames, events and actions. Fix what is found, and record the review like T-0701.
  - **Done when:** the review document lists each surface with its checks; findings are fixed or recorded as accepted risks in §15.

- [x] **T-1704 · Release 1.0.0**
  - **Deps:** T-1701, T-1703
  - **Do:** Release as in §17 (item 10): versions to `1.0.0`, `CHANGELOG.md` section, tag `v1.0.0`.
  - **Done when:** the release job publishes the `1.0.0` and `1.0` image tags for both architectures and the GitHub release.
